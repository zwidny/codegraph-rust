# CodeGraph MCP value: retrieval layer (L1)

Date: 2026-11-04
Tool: `scripts/benchmarks/mcp_value.py`
Scope: **locating code**, not agentic task success. L1 isolates the retrieval step so it
can run without a model and be reproduced after any re-index.

## Method

Two arms answer the same questions against the same index, with the same inspection
budget (`--budget-files 3`):

| Arm | What it does |
|---|---|
| `grep` | Iterative `rg -l -F <keyword>` refinement (falls back to `grep -rIl`), then reads the first 3 readable candidates. Skips non-code suffixes and files over 1 MiB, which is what an experienced agent does anyway. |
| `codegraph` | One `semantic_code_search` MCP stdio call, same 3-candidate budget. |

Tasks are sampled from the project's own index (`--generate`, fixed `--seed`), keeping
only **unambiguous** symbols: a name that appears exactly once in the project and is at
least 8 characters long. Without that filter the set fills with `format`, `info`,
`assert` and the benchmark measures noise instead of retrieval.

Two question shapes:

- `symbol` — "Where is `name` defined?" (a name-only question; the grep arm's home turf)
- `concept` — the first prose comment of a documented node (no symbol name given)

Metrics: `hit@1`, `hit@3` (both arms capped at 3 candidates), miss rate, rounds/calls,
bytes an agent would read, wall time.

## Results

### codegraph-rust (Rust, 251 files, 22,379 nodes)

| arm | hit@1 | hit@3 | miss | rounds/calls | bytes read | latency |
|---|---|---|---|---|---|---|
| grep | 79% | 100% | 0% | 1.8 | 67.5 KB | 1.07 s |
| codegraph | **93%** | 100% | 0% | 1.0 | **18.1 KB** | 0.94 s |

### entity_engine_v3 (Python, 511 files, 12,164 nodes)

| arm | hit@1 | hit@3 | miss | rounds/calls | bytes read | latency |
|---|---|---|---|---|---|---|
| grep | **79%** | **86%** | **14%** | 1.0 | 64.1 KB | **0.27 s** |
| codegraph | 64% | 79% | 21% | 1.0 | **19.4 KB** | 0.91 s |

## What this shows

1. **Reading volume is the stable win.** `codegraph` returns 18–19 KB per question in
   both projects, versus 64–68 KB for the grep path — a 70–73% reduction, independent of
   language or symbol shape.
2. **Symbol lookup is grep's home turf, and on Python it wins outright.** Test names like
   `test_high_threshold_lets_apples_fly` are unique identifiers; a literal search hits on
   round one, while embeddings blur them. Reporting this honestly is part of the result:
   CodeGraph is not a grep replacement for "I know the name".
3. **`codegraph` buys fewer wrong-file reads on Rust**, where symbols are shorter and more
   heavily overloaded across crates (79% → 93% hit@1, 1.8 → 1.0 rounds).
4. **L1 cannot show the main benefit.** Impact analysis, call chains and "what breaks if I
   change this" are multi-hop questions that a single-file grep cannot answer. They are
   measured in the impact layer below.

## Reproduction

```sh
python3 scripts/benchmarks/mcp_value.py --generate 14 --limit 10 \
        --markdown report.md --json-out report.json
python3 -m unittest discover -s scripts/benchmarks -p 'test_*.py'
```

`--generate` samples from the live index with a fixed seed; pass `--tasks` to replay a
frozen set. The same command runs against any indexed project.

## Known limitations (L1)

- File-level ground truth only; a hit at the right file with the wrong symbol still counts.
- Task syntax (`Where is X defined?`) is not how a human phrases an issue; real questions
  carry intent but also ambiguity, which this set removes by construction.
- The grep arm is modelled, not observed: an actual agent may refine differently.
- Non-ASCII prose can not be fairly searched by `grep`, so such `concept` tasks are
  skipped rather than counted as CodeGraph wins.

# Impact layer (L1.5): who calls this

Same harness, `--mode impact`. A target is sampled from the index when its incoming
`calls` edges form a 2–8 caller set; ground truth is the caller's definition file. The
question is "who calls `target`".

Read `recall` carefully: it is **not** symmetric evidence. The grep arm greps the target
name, so every file that mentions it — the definition, comments, strings — becomes a
candidate; that inflates recall while dragging precision down. The codegraph arm can only
report edges that the resolver actually built, so its recall is bounded by the project's
call resolution rate (63.7% for entity_engine_v3, ~58% for codegraph-rust).

### codegraph-rust (15 targets)

| arm | caller recall | precision | found all | bytes read | latency |
|---|---|---|---|---|---|
| grep | **98%** | 69% | 93% | 62.2 KB | 1.05 s |
| codegraph | 93% | **100%** | 87% | **6.3 KB** | **0.14 s** |

### entity_engine_v3 (15 targets)

| arm | caller recall | precision | found all | bytes read | latency |
|---|---|---|---|---|---|
| grep | 83% | 67% | 60% | 62.9 KB | 0.29 s |
| codegraph | **100%** | **100%** | **100%** | **5.7 KB** | **0.12 s** |

## What the impact layer shows

1. **Precision is where the graph wins.** 100% versus 67–69%: the caller list a tool
   returns is already a caller list, while grep hands back every textual mention and makes
   the agent decide which ones are real calls.
2. **The byte and latency gap widens to ~90% and 7–8×.** A single `get_reverse_dependencies`
   call replaces one grep plus reading three files, and the payload is 6 KB instead of 62 KB.
3. **Recall depends on resolution, not on the tool.** On the Python project every caller
   was found; on Rust the graph missed the callers that never resolved into an edge
   (macro-generated calls, trait dispatch), while grep's textual hit still matched them.
   A tool with perfect recall and 69% precision still costs the agent the judgement work.
4. **This is the layer that L1 could not reach.** Locate questions barely separate the two
   arms; impact questions separate them clearly in accuracy, tokens and latency.

## Reproduction

```sh
python3 scripts/benchmarks/mcp_value.py --mode impact --generate 15 --budget-files 3
```

## Known limitations

- Caller sets are capped at 2–8 so every answer stays checkable; a 300-caller hub would
  only measure the sampling budget.
- Definition files, not call sites: the graph reports where a caller lives, and the ground
  truth matches that. Call-site level scoring would need `metadata.source_file` per edge.

# Call-chain layer (L1.6): what does this eventually call

Same harness, `--mode chain --depth 2`. A start node is sampled when its outgoing `calls`
closure at depth 2 reaches 3–15 distinct files; ground truth is that closure. The question
is "what does `target` eventually call".

The grep arm needs two hops: grep the start name, read its hits, extract the symbols those
files call, grep each of them. That is where the cost lives.

### Two grep strategies, both measured

| hop-2 strategy | Rust recall / precision | Python recall / precision |
|---|---|---|
| keep **every** hit of every called symbol | 71% / **1%** | 82% / **0%** |
| keep the **first** hit of each symbol, ≤12 extra files | **26%** / 12% | **15%** / 7% |

Both extremes fail, in opposite directions: the untruncated set explodes into hundreds of
files, the truncated set loses most of the answer. There is no budget at which textual
two-hop search stays both cheap and complete. The table below uses the second (more
careful) strategy.

### codegraph-rust (12 starts, depth 2)

| arm | recall | precision | found all | grep calls | bytes read | latency |
|---|---|---|---|---|---|---|
| grep | 26% | 12% | 0% | 20.6 | 53.2 KB | 21.6 s |
| codegraph | **100%** | **94%** | **100%** | 1 | **10.8 KB** | **0.22 s** |

### entity_engine_v3 (12 starts, depth 2)

| arm | recall | precision | found all | grep calls | bytes read | latency |
|---|---|---|---|---|---|---|
| grep | 15% | 7% | 0% | 20.1 | 32.3 KB | 5.9 s |
| codegraph | **100%** | **100%** | **100%** | 1 | **18.2 KB** | **0.22 s** |

## What the chain layer shows

1. **This is the largest gap of the three layers.** Recall 100% versus 15–26%, and complete
   answers 100% versus 0%. A two-hop question is where "read a few files" stops being a
   strategy.
2. **The cost is 20 grep invocations and 6–22 seconds** versus one call and ~0.2 seconds.
   The latency gap is two orders of magnitude, not a few percent.
3. **Precision never recovers for grep.** Even the careful variant stays at 7–12%, because
   a hit on a symbol name is not a hit on a call site.
4. **codegraph stays bounded** because the traversal happens in the store; the payload is
   the answer, not the search space.

## Reproduction

```sh
python3 scripts/benchmarks/mcp_value.py --mode chain --generate 12 --depth 2
```

## Known limitations

- The grep arm is a model of an agent, capped at 20 symbol greps and 12 extra files; a
  smarter baseline might score higher, but the two strategies above bracket the space.
- Depth 2 only. Deeper chains widen the gap further and are not measured here.
- Same file-level scoring and same 3–15 reachable-file sampling bound as the impact layer.

# Agent layer (L2): real merged commits, real edits

`scripts/benchmarks/agent_value.py`. Each task is a merged commit that touched one code
file in 6–60 lines (fixes first). The agent starts from `sha^` in a throwaway
`git worktree`, receives the commit subject as the problem statement, and must edit the
repository. Ground truth is the file set the real commit changed.

Both arms share the model, the prompt skeleton, the 10-step budget and the JSON action
protocol; only the tool list differs:

| arm | tools |
|---|---|
| baseline | `read_file`, `grep`, `list_files`, `apply_patch`, `done` |
| codegraph | the same plus `semantic_code_search`, `get_reverse_dependencies` over MCP |

Model: `deepseek-flash`, temperature 0.

## Results (8 tasks)

| arm | solved | recall | precision | steps | tokens | seconds |
|---|---|---|---|---|---|---|
| baseline | 38% | 38% | 38% | 12.5 | 48,970 | 19 |
| codegraph | 38% | 38% | 38% | 11.8 | 51,993 | 23 |

Per task:

| task | baseline | codegraph | tokens (base / cg) |
|---|---|---|---|
| t01 project_id verification query | 0/1 | 0/1 | 71,747 / 63,790 |
| t02 tool call limits for Rig agents | 1/1 | 1/1 | 73,609 / 72,800 |
| t03 clarify semantic question prompts | 0/1 | 0/1 | 58,261 / 124,890 |
| t04 clarify architecture prompts | 0/1 | **1/1** | 40,395 / 47,256 |
| t05 captured runtime handle for tokio::spawn | 1/1 | 1/1 | 54,750 / 49,332 |
| t06 verification response handling | 0/1 | 0/1 | 26,376 / 10,044 |
| t07 reduce over-engineered batch sizes | 0/1 | 0/1 | 39,133 / 20,843 |
| t08 local tokenizer file in LM Studio | **1/1** | 0/1 | 27,493 / 26,990 |

## What the agent layer shows — including the negative result

1. **No measurable advantage at this difficulty.** 3/8 versus 3/8 solved, identical
   recall and precision, tokens within 6%. With n=8 the confidence interval is far wider
   than any effect, so the honest reading is "not distinguishable", not "equal".
2. **The tasks sit in grep's comfort zone.** Single file, 6–60 lines, and a commit subject
   that already names the subsystem. That is exactly the `locate` case where L1 showed grep
   is competitive.
3. **Model capability is the ceiling.** The agent fails 5 of 8 tasks in both arms, so most
   of the variance comes from whether the model can produce a correct patch at all, not
   from how it found the file.
4. **Token accounting is unstable.** t03 cost 2.1× more with CodeGraph because the model
   looped on unparseable replies; one task swings the arm-level mean by ~15%.
5. **The three cheaper layers are where the value showed up.** Reading volume (−73%),
   impact precision (100% vs 69%), and two-hop recall (100% vs 15–26%) are all measurable
   without a model, and none of them required the agent to write a correct patch.

## What would settle the question

- **Harder tasks**: multi-file changes or caller updates, where "did you find everything"
  decides success. L1.5/L1.6 predict CodeGraph wins there; L2 as built cannot see it.
- **A stronger model**: at 62% failure the benchmark measures the model, not the tooling.
- **More tasks**: n≥30 with paired scoring (McNemar) to put a confidence interval on the
  solve-rate difference.
- **Test-based scoring** instead of file overlap: `cargo test` on the edited worktree would
  separate "touched the right file" from "actually fixed it".

## Reproduction

```sh
python3 scripts/benchmarks/agent_value.py --tasks 8 --max-steps 10 \
        --json-out agent.json --markdown agent.md
```

## Known limitations

- File-level ground truth: editing the right file with a wrong edit still counts as solved.
- The index is built from the current checkout while worktrees sit at `sha^`; paths are
  stable, contents may differ slightly.
- Commit subjects name the subsystem, which helps both arms locate the code; real issue
  reports are usually vaguer.

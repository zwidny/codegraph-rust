# CodeGraph MCP value: retrieval layers

Date: 2026-11-04
Tool: `scripts/benchmarks/mcp_value.py`
Scope: **retrieval**, not agent task success. These layers run without a chat LLM, so the
numbers are reproducible and cheap to re-measure.

## Method

Two arms answer the same questions against the same index, with the same inspection budget.

| Arm | What it does |
|---|---|
| `grep` | Grep with line numbers (`grep -rn` / `rg -n -m 3`, output capped at 40 rows), then read a ±40 line window around each hit. Cost = search output + those windows. |
| `codegraph` | One tool call: `semantic_code_search` (locate), `get_reverse_dependencies` (impact) or `get_transitive_dependencies` (chain). Cost = the full JSON payload. |

Both numbers are "bytes that enter the agent's context". **The baseline is deliberately not
"read the whole file"** — an agent that greps for a line number then reads 80 lines around it
spends far less, and modelling it otherwise inflates the comparison. Averages are reported
next to medians because one outlier file can otherwise carry the mean.

Tasks come from the project's own index with a fixed seed. Locate tasks keep only
unambiguous symbols (unique name, ≥8 chars). Reproduce with the commands at the end.

## L1 — locate a symbol

| Repo | Arm | hit@1 | hit@3 | bytes (mean) | bytes (median) | latency |
|---|---|---|---|---|---|---|
| Rust (251 files) | grep | 79% | 100% | 10.2 KB | 5.3 KB | **8 ms** |
| Rust | codegraph | **93%** | 100% | 18.1 KB | 19.2 KB | 906 ms |
| Python (511 files) | grep | **86%** | **100%** | **3.9 KB** | **3.2 KB** | **8 ms** |
| Python | codegraph | 64% | 79% | 19.4 KB | 19.9 KB | 823 ms |

**grep wins the locate case.** It reads 2–5× less, answers ~100× faster, and on Python it is
also more accurate. The graph arm's latency is an embedding round trip, not graph traversal.

## L1.5 — who calls this

| Repo | Arm | caller recall | precision | bytes (mean) | latency |
|---|---|---|---|---|---|
| Rust (15 targets) | grep | **94%** | 70% | 8.5 KB | **6 ms** |
| Rust | codegraph | 93% | **100%** | 6.3 KB | 115 ms |
| Python (15 targets) | grep | 100% | 69% | 9.2 KB | **8 ms** |
| Python | codegraph | 100% | **100%** | 5.7 KB | 121 ms |

Precision is the graph's contribution: 100% versus 69–70%. grep's recall is not comparable
evidence — every textual mention of the name counts, including the definition, comments and
strings. The cost is latency: a SQL traversal takes ~120 ms against grep's ~7 ms.

## L1.6 — what does this reach (depth 2)

| Repo | Arm | recall | precision | search calls | bytes (mean) | latency |
|---|---|---|---|---|---|---|
| Rust (12 starts) | grep | 26% | 12% | 20.6 | 101 KB | **126 ms** |
| Rust | codegraph | **100%** | **94%** | 1 | **10.8 KB** | 235 ms |
| Python (12 starts) | grep | 15% | 7% | 20.3 | 78 KB | **149 ms** |
| Python | codegraph | **100%** | **100%** | 1 | **18.2 KB** | 174 ms |

Two hops is where the graph stops being optional: 100% recall against 15–26%, one call
against twenty, and 4–9× less reading. grep cannot recover here by tuning — narrower
keywords lose the answer, wider ones flood the context.

## What this shows

1. **Value depends on the question shape, not on the tool.** Locate: grep. Callers: precision
   from the graph. Two hops: the graph only.
2. **Reading cost is small either way** (4–20 KB per query). The interesting differences are
   accuracy and latency, not tokens.
3. **The graph's latency has two very different sources.** `semantic_code_search` pays an
   embedding round trip (~0.9 s); `get_reverse_dependencies` and `get_transitive_dependencies`
   are pure SQL (~0.1–0.2 s). Only the first is expensive.
4. **An earlier version of this benchmark was wrong** and is worth recording: it charged the
   grep arm for entire files and reported −73% / −90% reading savings and a 98× speed win.
   Neither survives a realistic grep-then-read-window model. The tables above replace those
   numbers.

## Reproduction

```bash
python3 scripts/benchmarks/mcp_value.py --generate 14 --limit 10
python3 scripts/benchmarks/mcp_value.py --mode impact --generate 15 --budget-files 3
python3 scripts/benchmarks/mcp_value.py --mode chain --generate 12 --depth 2
python3 -m unittest discover -s scripts/benchmarks -p 'test_*.py'
```

## Known limitations

- File-level ground truth: the right file with the wrong symbol still counts.
- The grep arm is a model of a careful agent (line numbers, ±40 line windows, capped output);
  a less careful agent would score worse and a smarter one marginally better.
- `semantic_code_search` latency includes a live embedding call, so it depends on the provider.
- Non-ASCII prose cannot be searched fairly by grep, so such `concept` tasks are skipped.

# Agent layer (L2): real merged commits, real edits

`scripts/benchmarks/agent_value.py`. Each task is a merged commit touching one code file
in 6–60 lines (fixes first, golden file ≤900 lines so the task is an edit and not a
navigation exercise). The agent starts from `sha^` in a throwaway `git worktree` and must
edit the repository. Ground truth is the file set the real commit changed.

Both arms share the model, the prompt skeleton, the step budget and the native tool-calling
protocol; only the tool list differs:

| arm | tools |
|---|---|
| baseline | `read_file`, `grep`, `list_files`, `apply_patch`, `done` |
| codegraph | the same plus `semantic_code_search`, `get_reverse_dependencies` over MCP |

Model: `deepseek-flash`, temperature 0, 18 steps.

## Three implementation defects found and fixed

The first run of this layer produced a meaningless tie. The step traces showed why:

1. **Protocol mismatch.** `deepseek-flash` is a thinking model that emits native DSML tool
   calls. The first harness asked for JSON text, so most steps were rejected as invalid and
   the retry policy ended runs early. Fixed by switching to the native `tools` /
   `tool_calls` protocol, and by passing `reasoning_content` back on the assistant turn
   (the API rejects the follow-up otherwise).
2. **The graph tools were never called.** In the first run the codegraph arm called
   `semantic_code_search` zero times in 12 steps: it behaved exactly like the baseline and
   simply had an unused tool attached. Fixed by naming the tools and their trigger in the
   system prompt.
3. **Transcript growth and over-trimming.** 12 steps accumulated ~55k prompt tokens; an
   early trim policy (600-character floor) made the agent re-read files it had already
   read. Fixed with a 90k-character transcript budget and a 2000-character floor.

## Results (6 tasks, 18 steps)

| arm | solved | steps | tokens | seconds |
|---|---|---|---|---|
| baseline | 17% (1/6) | 16.5 | 111,855 | 22 |
| codegraph | 33% (2/6) | 17.2 | 113,835 | 26 |

Per task, with the behaviours that explain the outcome:

| task | baseline | codegraph | notes |
|---|---|---|---|
| t01 tool call limits for Rig prompts | 0/1, 0 patches | **1/1, 3 patches** | the only clear separation; codegraph called the graph twice, then edited |
| t02 local tokenizer in LM Studio | 1/1, 2 patches | 1/1, 2 patches | both found it by grep |
| t03 parse embedded JSON fallback | 0/1, 0 patches | 0/1, 0 patches | both exhausted 18 steps reading |
| t04 Qwen dimension inference | 0/1, 0 patches | 0/1, 0 patches | same |
| t05 multi-turn tool iterations | 0/1, 0 patches | 0/1, 0 patches | 12 `read_file` calls, no edit |
| t06 tier-aware max_turns | 0/1, 0 patches | 0/1, 0 patches | same |

## What the agent layer actually shows

1. **The dominant failure is "reads forever, never edits".** 9 of 12 arm-runs emitted zero
   `apply_patch` calls. This is a model behaviour under a step budget, and it swamps the
   tool difference: with 9 of 12 runs producing no edit at all, the tool list can hardly
   matter.
2. **When the agent does decide to edit, the graph path is visibly shorter.** t01 is the
   archetype: two `semantic_code_search` calls → target file → three patches → solved,
   while the baseline spent all 18 steps reading and never wrote.
3. **The sample cannot support a rate difference.** 1/6 versus 2/6 has a confidence
   interval far wider than the effect. The honest statement is "not distinguishable at
   n=6", not "codegraph doubles the success rate".
4. **Token cost is roughly equal** (111k vs 113k), so the graph tools do not pay for
   themselves in prompt tokens at this task size — they pay off, when they do, in steps
   saved inside a run.
5. **This layer measures the model more than the tooling.** At 17–33% solve rate the
   variance is dominated by whether `deepseek-flash` will commit to an edit.

## What would settle it

- **n ≥ 30 with paired scoring** (McNemar) to put an interval on the solve-rate gap.
- **A stronger model**, so the ceiling is the tooling rather than "will it write a patch".
- **Tasks that force multi-file work** (update the caller when you change the callee).
  L1.5/L1.6 predict a CodeGraph advantage there; the single-file fixes measured here are
  exactly the case where grep already wins.
- **Test-based scoring** instead of file overlap, to separate "touched the file" from
  "actually fixed it".

## Reproduction

```sh
python3 scripts/benchmarks/agent_value.py --tasks 6 --max-steps 18 \
        --json-out agent.json --markdown agent.md
```

## Known limitations

- File-level ground truth: editing the right file with a wrong edit still counts as solved.
- The index is built from the current checkout while worktrees sit at `sha^`.
- Commit subjects name the subsystem, which helps both arms; real issues are vaguer.
- The step budget itself is a variable: 9 of 12 runs ended only because it ran out.
